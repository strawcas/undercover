# Plan for claim review and AgentCore Runtime

Build the four steps in [the Runtime brief](RUNTIME.md) in order. A senior handler can sign off a held approval or send it back with a note. The agent picks up the saved claim thread, and the backend coordinates work across laptop and Runtime sessions.

## Design

| Owner | Responsibility |
| --- | --- |
| Backend claim operations, `decision_records.py` and `database.py` | Own payment, review eligibility, current and returned decisions, the review timeline and shared claim ownership. Commit a handler's action before calling the agent through `backend/agent_service.py`. |
| `agent/harness.py`, `dispatcher.py` and `checkpoints.py` | Use the saved claim thread to pause and redetermine an approval. Keep the model-free dispatcher, up to 25 claim workers, independent savers and one four-connection pool per process. A dispatch uses its pinned version. A standalone resume uses the current version and has no run ID. |
| `agent/entrypoint.py` and the execution modules | Validate invocations, initialize once per process on request and register background work with the AgentCore app. Reuse `run_execution.py` for dispatch and evaluation and `improver.py` for rounds. Agent bookkeeping goes through `api.py` and `improver_api.py` on the shared backend transport. |
| Backend run and improvement operations | Admit one dispatch, standalone evaluation or actively working round across all sessions. Own creation, proposal review, heartbeat timestamps, stopped reasons and recovery. A round waiting for review releases the slot. A claim resume can work alongside the slot holder. |
| `backend/agent_service.py` | Own both invocation transports and classify results for the app. The laptop posts JSON over HTTP. The Lambda app invokes the configured Runtime ARN with the same JSON. |
| Dashboard | Use the existing typed API client, shared action and polling patterns, and brand styles. Show returned approvals, their notes and any current decision on the claim page, and show stopped reasons on the run and round views. |

Use FastAPI's required request models and one-line operation docstrings, SQLAlchemy transactions and LangGraph's interrupt and checkpoint APIs. Keep six operations in the Gateway OpenAPI document. Handler review and lease operations are app bookkeeping. Keep the existing security screen, approval limit and Gateway Policy in the decision flow. Claim execution receives no evaluation labels. The agent's goal on a returned claim is a policy-supported decision that addresses the senior handler's review and explains any referral. [Code standards](CODE_STANDARDS.md) · [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

Build on the existing `wait_for_sign_off` node, paid-claim resume route and process-local claim handoff. The working tree also contains changes for the post-commit sign-off call and for saving memory after settlement. Verify those changes against phase 1's criteria. The platform's staged package contains only `runtime/` and `agent/`. Current imports from backend authentication and screening settings, and from the context endpoint and catalog, must be resolved in product code for that package to work. Check the staged layout itself during phase 3.

Use disposable databases and stand-ins through all four phases. For each phase, run its offline checks, have a fresh reviewer check the diff against `CODE_STANDARDS.md`, fix findings, tick the verified items here, update `STATUS.md` and commit. ## Phase 1 — Pause a held approval and resume after sign-off

Make the existing pause consume the handler's answer with `Command(resume=...)` on the same thread and synchronous durability. Identify a pause from the checkpoint's pending interrupt. A checkpoint listing the pause node as its next step still needs to reach that interrupt. Test the handoff when sign-off arrives in that window. Keep the pause node free of side effects before `interrupt()`. Held originals count as handled by a run, and held evaluation copies finish without a pause.

Let the backend settle sign-off in one short transaction using the verified senior handler and the locked, unpaid claim. Use the common waiting-for-sign-off state for review. An unpaid approval blocked by a lower current limit must still be able to reach that state so a senior handler can settle it. Once committed, invoke `resume_claim` with the claim ID alone. Return the committed claim even if invocation fails, and log a warning. The agent reads the recorded sign-off and payment, verifies the saved pause and resumes outside the run, bypassing the run slot. It ends the graph without calling payment again. Determine payment or hold before starting approval memory writes, including for a Gateway denial. A held approval becomes eligible for memory when its paid sign-off resumes the graph. Preserve replay of eligible memory writes already started. Document the known gap when a paid claim never resumes and its memory has yet to be saved.

## Phase 2 — Send a held approval back

Add a senior-only `send_back_claim` app operation with a required nonblank note of up to 1,000 characters. Use the same claim lock and fresh state check for sign-off and send back, including a conditional write that serializes the two actions on SQLite. Reject copies and ineligible claims with 409. In one transaction, preserve the full decision and review attribution in claim history, append the note as a timeline step, clear the current decision, payout calculation and hold state, and set `sent_back`. Retain the thread and earlier steps. After commit, use the same best-effort invocation pattern as sign-off.

Add a keyed app operation that atomically takes a sent-back claim for either a standalone resume or a dispatch. Persist the claim's owner and last heartbeat. A standalone resume refreshes its claim record of work every minute, outside any run. Include sent-back claims in oldest-first dispatch selection, skip claims with a fresh standalone resume, and check ownership again when a worker takes a claim. After five minutes without a heartbeat, the next dispatch can carry the existing thread on. It supplies the stored review when the thread is still interrupted and continues the saved state when the answer has already been applied. Bind heartbeats and completion to the current ownership so a late worker cannot release or renew another worker's claim.

Have the graph clear its prior decision and reset its model-call allowance when it consumes the review. Carry forward the saved screen on the same thread, and keep the review if ordinary failure handling starts a fresh, screened attempt. Give the model a message naming the senior handler and quoting the review as feedback on the decision. The message's code-owned guidance requires checking the review against the policy wording and manual, and referring with a reason when the wording does not support the requested change. A replacement decision uses the ordinary validation, calculation and payment rules and can itself be sent back. Bind calculation, decision, payment and memory writes to the current decision revision so a delayed worker cannot apply a superseded result on the same thread. Supply the revision from the graph context and preserve the six Gateway operations. Edit only the decision-finality wording in `backend/instructions/claim.md`. Update `SPEC.md` for the workflow.

Extend the current decision panel with **Sign off** and **Send back** for eligible seniors. Use the existing form and polling patterns to preserve the note while editing and show the committed outcome promptly. Add **Sent back** to the queue, show returned decisions with their notes, senders and timestamps beside the current decision, and display the notes in the timeline. Tell the handler when a sent-back claim is waiting for the next dispatch.

## Phase 3 — Serve the agent through AgentCore

Create `agent/entrypoint.py` with one `BedrockAgentCoreApp` entrypoint. Validate required inputs before work is scheduled. Start with the existing work operations and `resume_claim` under their operation IDs, mapping the brief's `agents` input for dispatch to the existing concurrency field. Answer with `{"accepted": true}`, `{"refused": "<reason>"}` for a work refusal, or `{"healthy": true}` for health. Unknown operations and invalid inputs return 400. Register each job before replying, run it in a worker thread and complete its AgentCore task in a cleanup block even on failure. Use the app's `/ping` for busy status. Keep the interim work slot and abandoned-run recovery for this phase only.

Initialize lazily and serialize the first successful initialization. On Runtime, detect the deployment's `AGENTCORE_CREDENTIAL_<NAME>_NAME` settings, reseed Python's random state, and use AgentCore Identity's `requires_api_key` on the request thread to fetch `OPENROUTER_API_KEY`, `UNDERCOVER_API_KEY` and `DATABASE_URL`. Open the shared checkpoint pool only after settings are available. Failed initialization returns an error, releases partial resources and lets the next request try again. The health invocation initializes the agent too. Off Runtime, require the shared key as a bearer token for work, checking it with constant-time comparison. Runtime uses AWS invocation authorization. Calls from the agent to the backend retain the app's `X-API-Key` contract.

Switch `npm run dev` to the AgentCore entrypoint on `127.0.0.1:8080` with reload. Post to `/invocations` at `UNDERCOVER_AGENT`, which defaults to `http://127.0.0.1:8080`, with a 10-second timeout and `Authorization: Bearer <key>`. If `UNDERCOVER_AGENT_RUNTIME` is set, use the app region's `boto3` client, a fresh session ID of at least 33 characters, and a single attempt with 5-second connect and 20-second read limits. Read and close the response stream. Classify refusal, failure to connect, and explicit upstream errors as work the agent did not take. Treat a timeout or broken answer after sending as uncertain. Forward the refusal reason as 409 and tell handlers to reload when the outcome is uncertain. Keep agent credential failures distinct from handler 401s. [AWS invoke API](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_InvokeAgentRuntime.html) · [Boto3 response contract](https://docs.aws.amazon.com/boto3/latest/reference/services/bedrock-agentcore/client/invoke_agent_runtime.html)

Require the Gateway configuration on Runtime. Send model app tools, context calls and graph payment through the Gateway, signed with the Runtime role. Memory uses that role when configured. Screening and bookkeeping continue through the direct keyed app connection. Keep local Langfuse trace sessions and tags, and exercise the Runtime path with Langfuse credentials absent.

Set `prepare_threshold=None` in the shared checkpoint pool. Add `bedrock-agentcore`, a minimal locked `runtime` group and `boto3` in the `server` group. Resolve cross-package imports at the wire and configuration boundaries so the staged agent runs independently and the Lambda app and context packages keep their existing layout. Verify that the agent's tool input schemas and screening defaults still match the services and the configured model override. Add `runtime/` to Ruff and Pyright. Add an isolated, locked, offline import of `runtime.main` to `npm run check`, with a staged-package check that cannot pick up `backend/` or `context/` from the checkout. Move the Playwright stand-in to `/invocations` and readiness to `/ping`. Clear inherited Runtime settings in automated tests.

## Phase 4 — Coordinate work in the backend

Use a single seeded database lock row to serialize admission on both PostgreSQL and SQLite. Acquire it with a write in a short transaction. Check stale work and the current slot holder, then create the run or round, or record the verified handler's review. Commit and release the connection before invoking the agent. Resolve the verified handler using this transaction or a completed auth lookup so the request never has two database connections checked out or holds one during the agent call. A competing start gets 409 naming the active work. Preserve the existing one-open-round rule while allowing dispatch or standalone evaluation during a pending proposal review.

Replace the start and proposal payloads with `work_run(run_id)`, `work_round(round_id)` and `carry_round_on(round_id, proposal_id)`. `resume_claim(claim_id)` and `health` keep their payloads. Reuse current backend logic to pin run configuration, create evaluation copies and snapshot round settings. Keep the nested evaluation creation path for the improver. The worker reads the stored review and reason and resumes the saved interrupt. Keep the submitted review reversible until work is taken. Separate recording a review from applying its approval side effects so a refused invocation cannot publish a recipe or leave an approved candidate tied to a pending review.

On definite rejection or failure to take the work, use a new transaction to stop the created run or round with the reason, or restore the proposal to waiting for review. Scope the undo to that admission or review so it cannot overwrite newer state. On an ambiguous reply, leave the committed state in place for the handler to reload. Move the handler's round stop into the backend and let in-flight workers drain under existing state guards. Remove the process-wide work slot and startup stopping. Validate that each requested run is running and each round can work before accepting. A worker failure stops only its own record, including a round's running evaluation when the parent stops. Preserve completed results and billed usage. Keep checkpoint cleanup scoped to terminal evaluation runs, including evaluations stopped after their workers disappear.

Send a heartbeat by run, round or claim-resume ownership once per minute for the length of the work, even during a long model call or grading. A round's heartbeat covers its evaluations. When a handler next asks to start work, check the later of that work stretch's start time and its latest heartbeat. Stop work at five minutes of silence with **The agent stopped answering**, then admit the new work. Stop an improver's evaluation with its parent round. Keep pending reviews out of stale-work recovery. Show stopped reasons in the dispatch, Scoreboard and Improvement views using server records. Update the Playwright stand-in to use the keyed backend operations to finish or stop the app-created work by ID.
