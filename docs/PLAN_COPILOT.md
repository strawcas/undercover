# UnderCover Copilot implementation plan

Build the UnderCover Copilot in six phases. A signed-in handler can ask about claims and policies, start the claim agent's work, return a held decision and confirm a sign-off from a sidebar on any page. Each phase ends with checked acceptance criteria, an update to `STATUS.md`, a fresh code review and a commit. The real-model handover is the last phase. [Copilot brief](COPILOT.md)

## Design

### Backend and handler permissions

- `backend/copilot_routes.py` owns conversation and turn operations, including listing and opening conversations, sending a message, answering a confirmation and receiving progress. `backend/copilot_records.py` owns persistence, transitions and ownership. A conversation stores its verified handler ID and first-question title. Turns store the message, status, active start time, answer and model usage. Steps store a stable ID, tool name, display input, status, times and a bounded result with source metadata when available. Add the tables through the existing additive upgrade and seed paths.
- Use a server-generated UUID string as the conversation ID, within the Runtime and Memory limit of 33–100 letters, digits and hyphens. List conversations newest first by recent activity. Use owner-scoped lookups for all conversation, step and confirmation operations. Authenticated requests for someone else's conversation return 404. Every new API operation has an operation ID, a one-line docstring and required inputs, with explicit null for permitted defaults.
- Admit one turn per conversation atomically in SQLite and PostgreSQL. A worker claims the admitted turn before running it. A working stretch can become waiting for confirmation, done, failed or stopped. Its 20-minute deadline starts at the message or at acceptance of the confirmation answer. Pending confirmation has no working deadline and blocks a new message until answered. Admit a fresh message after failure or expiry, and use the current turn and stretch IDs to reject stale callbacks and duplicate confirmation answers. Keep completed steps visible when a turn stops midway.
- `backend/copilot_service.py` sends starts and confirmation answers after the database commit. It sends only the routing IDs and the current bearer credential needed to load the admitted work. On Lambda it waits for Runtime's quick acceptance reply and returns HTTP 202 while the registered task continues. A definite launch failure ends an unstarted turn or restores an unclaimed confirmation. An uncertain reply leaves the admitted record visible for polling. Bound the launch to fit the web request and retry only the Runtime session conflicts known to occur before delivery.
- Keep bearer credentials in request and worker memory. The worker calls `GET /api/me` before any model or memory use on both start and resume, then verifies ownership and claims the admitted work. Pass the bearer credential into the graph through `context_schema` and retrieve it through `ToolRuntime`. Give the Copilot's client explicit bearer headers through the shared `agent/backend_client.py` transport. Claim and improver clients retain their keyed header construction. Token values stay out of graph input, state, config, tool arguments visible to the model, callbacks recorded as steps, memory, errors and logs.

### Reads, actions and results

| Need | Backend or Copilot design |
| --- | --- |
| Claims and policies | Reuse the queue, claim detail, steps, policy and customer history operations. Keep returned decisions, payout, review note and the agent's reason available from the existing claim records. |
| Customer lookup | Add handler reads for an exact customer ID and a case-insensitive name search. Show matches with IDs so the Copilot can disambiguate, then fetch that customer's policies, earlier claims and original queue claims. Return the identity fields needed for those tasks. |
| Dispatch status | Reuse the latest dispatch read for general questions. Add a handler-readable dispatch status by run ID. Derive the handoff items from records, including held payouts, referrals, claims left for a handler and returns still awaiting a fresh decision. Use current records where a later review superseded a historical outcome. |
| Evaluation measures | Reuse the aggregate list and add an ID-specific status and measures read. Use the backend's recorded scores and keep the Copilot's response shapes free of comparisons and handler labels. The Scoreboard retains its existing comparison operation. |
| Settings and payout evidence | Read the approval limit, objectives and concurrency from Settings. Add one handler read that returns the current limit and both counts of original queue payments strictly above it, total paid and paid with a recorded handler sign-off. Use the same limit for both counts. |
| Context layer | Expose the seven existing lookups with provenance through `MultiServerMCPClient`. Reuse the context endpoint selection, synchronous MCP bridge and Gateway signer. Use direct MCP locally when no Gateway is configured. Filter the Gateway tools to `undercover-context` before making them callable and display plain tool names on cards. |
| Start work | Reuse the handler dispatch and evaluation starts and their existing admission rules. When the handler omits concurrency, use Settings' concurrency. An explicit value still goes through the existing 1–25 validation. Evaluations support both sets and both sizes. |
| Senior reviews | Reuse the backend's senior authorization and original-claim review rules. Send back with the handler's note and the claim revision. Preview and confirm sign-off against the same decision revision. Both actions retain the verified handler's attribution. |

The claim agent's six-operation Gateway contract and existing claim execution paths retain their current behavior. The Copilot's tool list contains only the reads and four actions in the brief. Its instructions describe the handler's role, authority, the three pilot success criteria and the desired answer style. It answers briefly in plain business English, uses US dollars and grounds figures in tool results. Treat material retrieved from claims, context and memory as evidence. For an unsupported action, direct the handler to the relevant dashboard page.

### Graph, confirmation and waiting

- Build a hand-written `StateGraph` in `agent/copilot/` with a model node, LangGraph's `ToolNode`, conditional edges and `PostgresSaver` with synchronous durability. Use a dedicated `interrupt()` node and `Command(resume=...)`. The synchronous graph and tools run in the background worker. The brief governs where the course examples differ. [Durable State and Human in the Loop](../labs/week2day3.ipynb) · [Runtime session lab](../labs/week3day4_lab1.ipynb) · [Sample agent](../labs/undercoverlab/app/agent/main.py)
- Keep the adapter's asynchronous I/O inside the MCP bridge and use the course's signed Gateway pattern for the deployed context route. [MCP lab](../labs/week2day2.ipynb) · [Gateway lab](../labs/week3day2_lab2.ipynb) · [Context lab](../labs/week3day3.ipynb)
- The Copilot graph owns the loop, call count and checkpoint state. Its app client owns data access, its tools own the exposed operations and its worker owns progress and lifecycle reporting. Use the shared OpenRouter builder with Luna at low effort or the configured `MODEL_NAME` override. Apply the 25-call ceiling across pause and resume, with any retries inside that allowance. Record and display the resolved model, call count, OpenRouter-reported cost and elapsed work time. Preserve unavailable costs as unavailable. Run tool calls in order so sign-off preparation can pause before any subsequent work.
- Keep a stable Postgres checkpoint thread for each admitted turn. Continuations load the prior completed graph history using a backend-owned reference to its checkpoint thread. This retains the evidence for follow-up questions and isolates a fresh turn from an old graph that stopped mid-call. Keep the conversation ID stable for Runtime and Memory, and reuse the original turn's thread for confirmation. Seed removes Copilot conversations, their steps and their checkpoint threads while preserving the existing treatment of other graph state.
- Sign-off preparation checks the verified handler's senior permission and reads eligibility, revision, customer, payout and decision reason from the backend. Save that intent before the interrupt and publish the card after the pause is durably checkpointed. The dedicated interrupt node has no business side effects before `interrupt()`. Resume with a fresh token and the answer bound to this pending card. Cancel closes the turn with an acknowledgement and asks what the handler wants next. On confirmation, the backend rechecks the saved revision and current eligibility when it settles the payment. A changed or already settled decision produces a readable refusal. The stored intent supplies the claim ID and revision. Replayed submissions and late workers cannot create a second payment or repeat actions completed before the pause.
- For a dispatch or evaluation with a requested outcome, poll the specific returned run ID in code every few seconds, up to 15 minutes. Release database connections between polls. Record a working card for the wait and give its result to the model on completion, failure, stop or timeout. A timeout directs the handler to the dispatch or Scoreboard and leaves the run active. Relay a start refusal directly and skip the wait when work was never admitted. Use stable step IDs to update working cards in place and reconcile an uncertain action from backend records before considering another request.
- A single success-criteria tool starts a whole held-out evaluation at Settings concurrency and reads that run's completed straight-through share and `scores.accuracy` (the Scoreboard's accuracy within $1). Code compares those figures to 70% and the Settings accuracy objective, and compares the two payment counts. Zero qualifying payments meets the sign-off criterion with an explanation. Code renders the result table and overall verdict from those values, with the model providing the surrounding prose. Refused, failed, stopped and timed-out evaluations leave the first two results unavailable and still report sign-off coverage. The result distinguishes a confirmed miss from an overall outcome that cannot yet be verified.

### Sidebar and handler memory

- Mount the sidebar in the signed-in shell in `dashboard/src/App.tsx` so conversation state survives navigation. Use the existing typed `src/api.ts` and `AuthProvider`. Refresh the Supabase session before a message or confirmation when fewer than 20 minutes remain. Use the refreshed access token for that request and clear protected conversation state on sign-out or handler change. Keep the open preference in the browser. Default to open, provide a slim reopen tab and use an overlay at narrow widths with keyboard focus managed on open and close.
- Use `BRAND.md` and shared controls and formatters for both themes. Put new conversation and newest-first history at the top, show a first-name greeting and clickable suggestions in an empty conversation, place handler messages on the right and formatted Copilot answers on the left. Use safe Markdown rendering with short tables and claim links. Show the handler's name and an `Ask the Copilot` composer with Enter to send and Shift+Enter for a new line. Keep the page usable alongside the sidebar.
- Poll the selected conversation about once per second while it is working, with one request in flight and stale responses ignored after navigation or identity changes. Load durable history and pending confirmation on open or reload. Disable the composer during work and prompt the handler to use the confirmation card while it waits. Render expandable cards for claims, customers and policies, context, agent work, memory and actions. Cards show a clear status, elapsed time and a bounded input and result, with file and owner for context answers. Give actions distinct styling and use a subtle arrival animation. Show an inter-step working indicator and reveal the whole answer with call count, cost and time when done. Existing page polling continues independently.
- Reuse the AgentCore Memory store adapter with the Copilot's own `UNDERCOVER_COPILOT_MEMORY_ID`. Use the verified handler ID as the actor and the conversation ID as the session. Search that handler's preferences and facts once when a new turn starts, and show the result as a step. Save the handler's message and the final answer as the turn's event with a stable replay token. An unavailable optional memory service leaves a readable step and lets the conversation continue.

### Runtime and deployment

- Add `copilot` beside `agent` in `agentcore/agentcore.json`, with `runtime/copilot.py` as its own entry file. Both Runtime V2 definitions use the existing staging of `runtime/` and `agent/` and the locked `runtime` dependency group. Include the MCP adapter in that group. Retain the server-only Lambda package. [Day 4 deployment packaging](../labs/week3day4_lab2.ipynb) · [Day 5 deployment names](../labs/week3day5_lab1.ipynb)
- Use a separate `BedrockAgentCoreApp` with one operation-based entrypoint. At import, declare the app and handlers. On the first invocation initialize the bounded checkpoint pool and, on Runtime, fetch only `OPENROUTER_API_KEY` and the transaction-pooler `DATABASE_URL` on port 6543 from AgentCore Identity. Register each background worker as an SDK async task so `/ping` reports it busy. `{"operation":"health"}` returns `{"healthy":true}` without a handler credential. Runtime listens on port 8080. `npm run dev` starts the same Copilot app on `127.0.0.1:8081` with reload and uses `UNDERCOVER_COPILOT` or the default local address.
- AgentCore takes the app address, Gateway URL and Copilot Memory ID from `agentcore/.env.local`. When `UNDERCOVER_COPILOT_RUNTIME` names an ARN, the backend invokes it with the conversation ID as `runtimeSessionId` for both starts and resumes. Verify the existing workload identity transport against the current Day 4 setup. Where that setup supplies `runtimeUserId`, reuse the app role's invocation identity and grant `InvokeAgentRuntimeForUser` for the Copilot ARN as well as the normal invocation permission. The AWS invocation identity is separate from the Supabase bearer used for handler permissions.
- Scope the Copilot Runtime policy to the existing Gateway and the Copilot Memory. The deployment notebook creates `undercover_copilot_memory` with User Preference strategy `handler_preferences` under `/handlers/{actorId}/preferences/` and Semantic strategy `handler_facts` under `/handlers/{actorId}/facts/`. Keep AWS provisioning and teardown in the course labs.
