# Tech stack

- `backend/` uses FastAPI and SQLAlchemy Core, with shared queries for SQLite and Postgres. Ordinary Postgres processes use the Supabase session pooler and the `undercover` schema, with at most four connections. SQLite uses `UNDERCOVER_DB` or `undercover.db`. Transactions commit before a response or background task. Every API operation has an operation id, one-line docstring and required inputs, including explicitly nullable fields.
  - `dependencies.py` owns request transactions. `auth.py` verifies Supabase tokens with PyJWT and asymmetric project JWKS, audience `authenticated` and the project issuer. Handler emails resolve authority and attribution. Private service traffic uses constant-time validation of `X-API-Key`. Shared reads accept either that key or a verified handler token. `GET /api/agent/openapi.json` generates the six-operation app contract for the Gateway.
  - `configurations.py` owns immutable configuration/recipe records, current pointers and `difflib` text changes; its claim-facing reads never include scores. `settings.py` owns platform values, model catalogue reads and attributed setting history. Decision inserts capture the approval limit through a scalar subquery with a PostgreSQL shared lock and retain it as the decision's sign-off threshold; SQLite uses the same atomic statement. Run creation resolves model/effort from its required version rather than client-supplied model fields.
  - `database.py` owns tables, seeding and shared claim views. Seeding loads 26 queue originals, including CLM-1901, and stores pristine evaluation sources and handler labels in separate tables and drops the retired to-do table before its parents. Rebuilding clears runs, copies, measurements and the scoreboard.
  - Seeding uses the plans and versioned documents from `context/`. The app keeps the latest payout calculation for the open attempt. Calculation and decision requests validate the thread under the claim lock. The decision record keeps the approved calculation, maker, timestamp and seeded manual version. A payout preview supplies a null thread ID.
  - `runs.py` owns membership, frozen results, deterministic summaries and attributed measurements; polling aggregates costs/time and live outcomes in a fixed query count. Member rows include customer identity, earliest work-slice start in this run, and elapsed completion time: decision time for declines/referrals, payment time for approvals. UTC timestamps retain subsecond precision. Closed rows freeze identity/timing alongside outcomes; legacy snapshots use bulk enrichment and leave unavailable or out-of-run timing null, without a migration or reseed. `evaluations.py` alone joins expected labels to agent results; `scoring.py` implements the lab formulas. Claim operations never read labels.
  - `agent_service.py` sends authenticated requests to the local agent service (`UNDERCOVER_AGENT`, default `http://127.0.0.1:8002`). An unavailable service returns 503 and a busy one returns 409. The backend settles senior sign-offs inside their own transaction.
  - `judge.py` is the only Decisions caller: Jev and the lab rubric, per-call `server_url` from `OPENROUTER_DECISIONS_URL` (origin, default `https://openrouter.ai`), 10-second timeout and no SDK retries. It preserves score, most-likely letter, both check probabilities and reported cost; failures remain ungraded. `evaluation_completion.py` reserves grading atomically, releases DB connections for parallel calls, then saves facts and freezes the run. Repeated completed finishes do not regrade; a concurrent finish is refused and a stop cannot be undone. Grade inserts and member freezing are batched. Frozen scores from completed full round-attributed evaluations alone form version averages; manual/tiny/stopped runs are excluded.
  - `improvements.py` owns captured settings/catalogue, proposal decisions, missing baseline counts, restricted reports and atomic activation. `improvement_rules.py` compares absolute accuracy/grade and relative cost/time with strict noise thresholds and inclusive tolerances. `improvement_budget.py` sums billing facts and quotes a whole candidate sequence plus individual runs; observations use each model's maximum recorded cost per selected claim, unseen models scale by the larger price ratio. Cold-start allowances are 50k input/10k output tokens per claim, plus at least $0.001 per claim for the judge (or the higher observed allowance). Unknown usage refuses new work. Round state writes stop after closure; received billing facts remain recordable. `improvement_routes.py` separates signed-in senior orchestration from internal service records.
- `agent/`: six parts, synchronous throughout for Windows compatibility. The improver uses `create_agent` with `read_results`, `propose_change`, `run_evaluation` and `propose_recipe`, medium Luna, disabled parallel tool calls, a persisted 30-call thread limit and HumanInTheLoopMiddleware on both proposals. Its separate `improver_api.py` exposes development evidence and held-out aggregates. Shared `backend_client.py` owns transport. `checkpoints.py` owns the single four-connection pool; claims and rounds use independent savers. `run_execution.py` runs nested evaluations in fresh contexts without reacquiring the service's work slot.
  - `models.py` is shared model construction from a backend configuration. Dispatch work requires its run's configuration version; the graph caches that version's prompt, with unchanged nodes/tools. The CLI resolves the same score-free configuration. `MODEL_NAME` overrides are resolved at seed time to the sole allowed model with effort `default` and zero catalogue prices; the builder omits a provider effort for `default`, keeping the real `none` distinct.
  - `api.py` owns the app operations. Its direct transport captures `UNDERCOVER_API` at import (default `http://127.0.0.1:8000`) and uses the configured API key. Bookkeeping, configuration, runs and screening use this route. Model app tools and graph payment use the selected route.
  - `gateway.py` signs streamable HTTP requests with SigV4 for `bedrock-agentcore` and maps the `undercover-app` and `undercover-context` tool names. `context_client.py` uses the unsigned local MCP endpoint or the Gateway's context target. `mcp_client.py` bridges tool calls to the synchronous graph with a private event loop.
  - `tools.py` exposes app and context tools through the same model schema on both routes. `ToolRuntime` carries claim, policy, customer, thread and configuration identity. `observations.py` records the actual tool names, typed artifacts and refusal sources for the dashboard.
  - `screening.py` uses a strict structured-output call on Luna at effort `none`, or the explicit model override with provider effort omitted. The graph checkpoints each result and retries up to three unreadable replies. Usage belongs to the run that made the call. A flagged claim receives a zero-payout referral with the screen's reason.
  - `harness.py` owns version-pinned graph execution, reservations, measurements and tracing. A claim gets its own `PostgresSaver` on a four-connection process pool. The graph saves screening, model, sequential tools, sign-off pause and payment with `durability="sync"`. Adjudication begins after screening. A resumed, settled sign-off uses the backend payment record.
  - `memory.py` uses `AgentCoreMemoryStore` with the AWS CLI's region and credential chain. Eligible graphs save two events after adjudication, with a stable event token for replay. Search uses the runtime customer's namespace and filters the current claim summary. Evaluation graphs have no store or memory tool.
  - `dispatcher.py`: a model-free LangGraph listing node and `Send` fan-out, additive results and `max_concurrency=N`. No dispatcher saver or shared claim thread. `RetryPolicy` retries only `ModelRateLimitError`/`ModelTimeoutError`, up to 3 tries; its error handler retains exhausted work. A narrowly guarded workaround handles LangGraph 1.2.12's rethrow of already-handled parallel futures (upstream issue 8277).
  - `service.py` is the private local FastAPI process on 8002. It requires its key at startup and supports one named dispatch, evaluation or improver work slot, synchronous worker execution, startup recovery and evaluation checkpoint cleanup.
  - `console.py` sets report logging; `uv run -m agent CLM-1001` remains the single-claim entry point. There is no no-id queue mode or cap.
  - Initial model: `openai/gpt-6-luna`, low reasoning effort. An explicit `MODEL_NAME` seeds a free-model configuration at recorded `default` effort. OpenRouter-reported tokens and `usage.cost` are stored per reply/claim/thread/run, idempotently, with missing values null. Monotonic cumulative slices exclude handler waits and downtime; run wall time is separate. Langfuse roots retain claim/thread sessions and carry `langfuse_tags: [run_id]` for current run work.
- `dashboard/`: React, Vite and strict TypeScript; its sole backend client is `src/api.ts`. Queue, claim, Configuration, Settings, Improvement, Scoreboard and evaluation detail pages poll live records. The shared hook serializes action refreshes behind pending polls; Improvement waits for every member of its request batch, including failures. Its senior actions use shared confirmation dialogs, backend-generated diffs and typed client operations. History retains terminal-state labels and rejected model/effort changes. Two SVG charts show held-out accuracy and grade with explicit scales and a shared version-score table; no scoring or orchestration rule runs in the browser. The dispatch's eight-column claims table shows customer, state, decision, payout, local start, elapsed time to finish and model cost. It distinguishes held/unpaid work, incomplete outcomes and unavailable historical timing; active claim time remains a separate summed measure. Semantic headers, existing chips/formatters and a horizontal scroll area serve desktop and narrow screens. Both start forms share the active-run contract. Evaluation copies have no sign-off form.
- `e2e/`: Playwright with an independent SQLite backend/dashboard and a stateful agent-service stand-in. Tests use stubs, never real models or `.env`.
  - The judge stand-in implements the actual Decisions HTTP shape. Backend test servers explicitly use its origin and an offline key, with `MODEL_NAME` empty so inherited shell overrides cannot alter grading. Python tests intercept either the public grading function or the SDK's HTTP transport. Null grades and costs stay unavailable; the UI converts probabilities to Yes/No at 0.5 and never rounds a score into a letter.

The dashboard's sole Supabase client is `src/supabase.ts`; `AuthProvider` restores and refreshes sessions, signs handlers in/out and clears protected content on failed verification or an action's 401. The backend client attaches the current access token. Supabase URL/publishable key are public browser configuration; `HANDLER_PASSWORD` is only for live verification and is never bundled. Vite loads root `.env` in development and reads the two public values for production builds. Browser tests use an isolated asymmetric Auth stand-in with local JWKS and CORS, and unit tests verify local signed tokens without real Auth.

JWT validation allows five seconds of clock skew for freshly issued tokens, retaining signature, issuer, audience and time checks. The shared dashboard loader associates data with its stable resource loader: a changed claim/evaluation cannot display the previous resource's data or actions. Temporary same-resource errors preserve content with retry; a 404 clears it. Shared page headers, model/effort comparisons, local table scrolling and accessible darker status fills keep the old and new pages consistent. Configuration provenance uses full local dates and times.

Settings converts accuracy and relative cost/time fractions to percentage values only at the form boundary, with accuracy changes labeled as percentage points. Grade values retain their 0–3 score units. A shared settings summary renders confirmation and before/after history in the same human-readable units. API payloads, audit records, captured round settings and backend comparisons retain their existing numeric representation; this display change needs no migration or reseed.

Improver trace stretches share the round id as their Langfuse session. Evaluation claim traces retain independent claim/thread sessions and carry both round and run tags. Verification uses the supported `/api/public/v2/observations` API; the older observations endpoint returns 410 for this project. Claim-model, improver and judge costs are stored separately; a dispatch cost is reported alongside round spending rather than counted inside it.

Round billing totals use one portable SQL aggregate across improver, claim and judge usage, preserving unknown charges. Claim admission and state guards take compatible shared parent locks; billing, quotes and round transitions retain exclusive locks. Judge completion explicitly takes the exclusive parent lock before saving its charges, without a lock upgrade. The run → round → claim order remains unchanged. This follows PostgreSQL's [row-lock compatibility rules](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS), allowing readers to proceed together while excluding billing and stop writers. Query-count, compiled-lock and stopped-round regressions protect this boundary; no client timeout or connection limit was increased.

`context/` preloads the governance catalog and serves seven read-only tools through FastMCP with stateless streamable HTTP and JSON responses. The local server listens at `http://127.0.0.1:8006/mcp`. The Lambda handler creates an MCP app for each invocation over the same loaded catalog.

Python 3.12 with uv and Node 26. `.env` supplies OpenRouter, Supabase, Langfuse and the local agent key. `npm run dev` starts the app, agent service, context service and dashboard. The CLI loads environment settings after imports and resolves the Gateway, context and memory settings when it builds a claim graph.

## Deployment

- `npm run build` compiles Vite to `dashboard/dist`. The build uses `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from the root `.env` or shell and bundles those two public values.
- Package `backend/`, its runtime data under `data/`, `dashboard/dist/` and the pinned `server` dependencies. Build Python 3.12 Linux x86-64 wheels into the archive.
- Lambda invokes `backend.main.handler` through Mangum with lifespan off. For a standalone web server, run `uv run -m uvicorn backend.main:app`. The packaged app serves the dashboard and its navigation paths alongside the JSON API.
- The Function URL app uses `DATABASE_URL`, `VITE_SUPABASE_URL` and `UNDERCOVER_API_KEY`. Seed the database before using it. With `AWS_LAMBDA_FUNCTION_NAME` set, the backend uses SQLAlchemy `NullPool`, disables psycopg prepared statements and selects the schema inside each transaction. Set `DATABASE_URL` to the Supabase transaction pooler on port 6543 for that runtime.
- `npm run check:server` imports the backend in a separate offline environment with only the locked `server` group.
- Package `context/` with its seven files and the locked `context` group's Linux Python 3.12 dependencies. Leave tests out of the archive. Deploy `context.server.handler` behind a Function URL with `AWS_IAM` and no environment variables. `npm run check:context` imports the handler in an isolated offline environment.
- The Gateway targets are `undercover-app` using the app's OpenAPI contract and API-key provider, and `undercover-context` using signed IAM access to the Lambda MCP endpoint. The course notebook sets up the targets, Policy and the two Memory strategies. [Week 3 Day 3 notebook](../labs/week3day3.ipynb)
- The laptop agent uses `UNDERCOVER_GATEWAY_URL` for signed tools when configured, `UNDERCOVER_CONTEXT` for the direct context endpoint and `UNDERCOVER_MEMORY_ID` for customer memory. Gateway and memory use the AWS CLI credentials and region. Direct app bookkeeping still uses `UNDERCOVER_API` and `UNDERCOVER_API_KEY`.
