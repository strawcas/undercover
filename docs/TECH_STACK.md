# Tech stack

- `backend/`: FastAPI and SQLAlchemy Core, with each query shared by SQLite and Postgres. `DATABASE_URL` selects the Supabase session pooler and the `undercover` schema, with at most 4 connections; otherwise SQLite at `UNDERCOVER_DB` or `undercover.db`. Requests commit before responses/background tasks. Every API operation has an operation id, one-line docstring and required inputs, including explicitly nullable fields. Payout/sign-off rules remain enforced by the backend.
  - `dependencies.py` owns request transactions; `auth.py` verifies Supabase bearer tokens with PyJWT and asymmetric project JWKS, audience `authenticated` and the project issuer. Handler emails resolve permissions. Handler starts need sign-in, sign-off needs senior authority and uses the token identity; internal agent writes remain without handler sign-in until Week 3.
  - `configurations.py` owns immutable configuration/recipe records, current pointers and `difflib` text changes; its claim-facing reads never include scores. `settings.py` owns platform values, model catalogue reads and attributed setting history. Decision inserts capture the approval limit through a scalar subquery with a PostgreSQL shared lock and retain it for payment; SQLite uses the same atomic statement. Run creation resolves model/effort from its required version rather than client-supplied model fields.
  - `database.py` owns tables, seeding and shared claim views. Seeding loads pristine queue/held-out evaluation sources and handler labels into separate tables and drops the retired to-do table before its parents. Rebuilding clears runs, copies, measurements and the scoreboard.
  - `runs.py` owns membership, frozen results, deterministic summaries and attributed measurements; polling aggregates costs/time and live outcomes in a fixed query count. Member rows include customer identity, earliest work-slice start in this run, and elapsed completion time: decision time for declines/referrals, payment time for approvals. UTC timestamps retain subsecond precision. Closed rows freeze identity/timing alongside outcomes; legacy snapshots use bulk enrichment and leave unavailable or out-of-run timing null, without a migration or reseed. `evaluations.py` alone joins expected labels to agent results; `scoring.py` implements the lab formulas. Claim operations never read labels.
  - `agent_service.py` is the only client of the agent service (`UNDERCOVER_AGENT`, default `http://127.0.0.1:8002`). Starts forward N/selection before creating any run; unavailable service is 503 and busy is 409. Sign-off sends a resume notification.
- `agent/`: five parts, synchronous throughout for Windows compatibility.
  - `models.py` is shared model construction from a backend configuration. Dispatch work requires its run's configuration version; the graph caches that version's prompt, with unchanged nodes/tools. The CLI resolves the same score-free configuration. `MODEL_NAME` overrides are resolved at seed time to the sole allowed model with effort `default` and zero catalogue prices; the builder omits a provider effort for `default`, keeping the real `none` distinct.
  - `api.py`: the only backend client (`UNDERCOVER_API`, default `http://127.0.0.1:8000`), one function per operation. No answer-key or comparison operation is exposed to the agent service.
  - `tools.py`: the seven unchanged claim tools, `ToolRuntime` context and saved claim state. Run identity is fresh runtime context, not checkpoint state.
  - `harness.py`: version-pinned graph construction, process checkpoint pool, claim execution, measurements, tracing and reservations. Each execution has its own `PostgresSaver` on one pool of at most 4 connections; setup runs once. The claim `StateGraph` has model, sequential tools, sign-off `interrupt()` and payment nodes, saved with `durability="sync"`. Instructions are cached per graph when its model first runs. Fresh backend-verified sign-off context permits payment after a pause or a stale decision checkpoint without an extra checkpoint lookup; telemetry follows payment. Direct execution starts a waiting claim; dispatch work starts or resumes through one harness function.
  - `dispatcher.py`: a model-free LangGraph listing node and `Send` fan-out, additive results and `max_concurrency=N`. No dispatcher saver or shared claim thread. `RetryPolicy` retries only `ModelRateLimitError`/`ModelTimeoutError`, up to 3 tries; its error handler retains exhausted work. A narrowly guarded workaround handles LangGraph 1.2.12's rethrow of already-handled parallel futures (upstream issue 8277).
  - `service.py`: FastAPI on 8002, immediate 202 admission with one atomic dispatch/evaluation slot, synchronous background execution away from the ASGI loop, startup recovery and evaluation checkpoint cleanup. Sign-off handoffs are reserved before scheduling and can wait for a worker reaching its pause.
  - `console.py` sets report logging; `uv run -m agent CLM-1001` remains the single-claim entry point. There is no no-id queue mode or cap.
  - Initial model: `openai/gpt-6-luna`, low reasoning effort. An explicit `MODEL_NAME` seeds a free-model configuration at recorded `default` effort. OpenRouter-reported tokens and `usage.cost` are stored per reply/claim/thread/run, idempotently, with missing values null. Monotonic cumulative slices exclude handler waits and downtime; run wall time is separate. Langfuse roots retain claim/thread sessions and carry `langfuse_tags: [run_id]` for current run work.
- `dashboard/`: React, Vite and strict TypeScript; its sole backend client is `src/api.ts`. Queue, claim, Configuration, Settings, Scoreboard and evaluation detail pages poll live records without overlapping slow requests. The dispatch's eight-column claims table shows customer, state, decision, payout, local start, elapsed time to finish and model cost. It distinguishes held/unpaid work, incomplete outcomes and unavailable historical timing; active claim time remains a separate summed measure. Semantic headers, existing chips/formatters and a horizontal scroll area serve desktop and narrow screens. Both start forms share the active-run contract. Evaluation copies have no sign-off form.
- `e2e/`: Playwright with an independent SQLite backend/dashboard and a stateful agent-service stand-in. Tests use stubs, never real models or `.env`.

The dashboard's sole Supabase client is `src/supabase.ts`; `AuthProvider` restores and refreshes sessions, signs handlers in/out and clears protected content on failed verification or an action's 401. The backend client attaches the current access token. Supabase URL/publishable key are public browser configuration; `HANDLER_PASSWORD` is only for live verification and is never bundled. Vite loads root `.env` for dev only. Browser tests use an isolated asymmetric Auth stand-in with local JWKS and CORS, and unit tests verify local signed tokens without real Auth.

Python 3.12 with uv and Node 26. `.env` holds OpenRouter, Supabase and Langfuse configuration. `npm run dev` passes it to the servers. The CLI loads model/database/tracing keys from it, while its backend address is captured from the shell when the API client is imported.
